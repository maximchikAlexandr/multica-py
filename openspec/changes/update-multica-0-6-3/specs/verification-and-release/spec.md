## ADDED Requirements

### Requirement: Multica 0.6.3 coverage extends existing tables
Offline verification SHALL extend the existing frozen contract, provenance, operation, response, model, resource, compatibility, documentation, and packaging tables. Positive and negative rows SHALL cover multi-value property encoding, presence, order, duplicates, null and empty values; project workflow null/UUID decoding; workflow validation, remap and handoff results; daemon commit legacy/full-SHA output; project partial updates; wakeup diagnostics; upload failures; and stable redacted errors. No parallel fixture framework or duplicate canonical operation row SHALL be introduced.

#### Scenario: Changed behavior has exact vectors
- **WHEN** focused unit, contract, and component tables run
- **THEN** complete argv, wire payloads, decoded results, validation ownership, call counts, and error/redaction behavior match every 0.6.3 delta scenario

#### Scenario: Retained behavior remains closed
- **WHEN** approved operations and all 196 response work items are compared with runtime discovery and test references
- **THEN** every item has exactly one supported verdict and unchanged items retain their existing public behavior

### Requirement: Complete 0.6.1 to 0.6.3 audits are reproducible offline
Maintainer evidence SHALL reproduce both official release identities, archives, checksums, version output, recursive help, pinned source registration, dynamic `checkin` resolution, the 209-node CLI inventory, and the 196-item response audit. Tracked files and distributions MUST exclude `.devlocal`, release archives, binaries, source checkouts, collector output, audit JSON, diagnostic logs, hashes, screenshots, and transient render directories.

#### Scenario: Approved contract reproduces from pinned inputs
- **WHEN** source-aware validation, deterministic double render, generated check, and source-link audit run
- **THEN** identities, counts, dispositions, mappings, generated bytes, and source links agree or a gate fails

#### Scenario: Evidence stays outside Git and packages
- **WHEN** tracked and built contents are audited
- **THEN** only approved contract/code/tests/docs/generated product artifacts are present

### Requirement: Delivery gates use one clean exact SHA
Strict OpenSpec validation, source-aware approved-contract validation, deterministic render comparison, generated freshness, source-link audit, Ruff check and format, mypy source and tests, complete non-live pytest and live-node exclusion, build, wheel/sdist package tests, and forbidden-content audits SHALL pass at one exact clean implementation SHA. GitHub CI fixtures required by this change SHALL be implemented by the Implementer; the independent Tester SHALL inspect and execute them without editing them.

#### Scenario: Offline acceptance is complete
- **WHEN** the implementation is presented for review
- **THEN** every mandatory offline command exits successfully at the reported SHA and the worktree remains clean

#### Scenario: Live verification is separately evidenced
- **WHEN** the prepared 0.6.3 target and human-approved live gate are available
- **THEN** the trusted workflow and independent Tester record the candidate SHA, observed CLI identity, commands, exit codes, assertions, and Multica-only evidence without committing logs or images

### Requirement: Documentation describes one direct migration and rollback
README, API, CLI coverage, compatibility, migration, contributing, service-usage, and release guidance SHALL describe one direct upgrade from effective baseline `0.6.1` to maximum-tested `0.6.3`, the interval `[0.6.0,0.6.4)`, approved additions, retained behavior, and explicit exclusions. Contract, generated projection, handwritten code, fixtures, tests, docs, and package claims SHALL roll back together to exact SDK baseline `a96eecf3e12a88dd7b4d56e1aafae3285fb0990c`.

#### Scenario: Consumer guidance matches implementation
- **WHEN** public docs, signatures, inventories, compatibility metadata, and fixtures are compared
- **THEN** multi-value properties, workflows, daemon commit, diagnostics, exclusions, and version bounds agree exactly

#### Scenario: Failed gate restores one baseline
- **WHEN** any provenance, generation, source-link, test, or packaging gate fails
- **THEN** all 0.6.3 changes and claims can be reverted together without using draft PR #101 or PR #103 as a baseline
