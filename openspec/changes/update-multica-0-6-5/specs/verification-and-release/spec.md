## ADDED Requirements

### Requirement: Multica 0.6.5 coverage extends existing tables
Offline verification SHALL extend existing frozen contract, provenance,
operation, response, model, resource, compatibility, documentation, and package
tables. Positive and negative rows SHALL cover property array encoding and
presence/order/duplicates/null/empty values; project workflow UUID/null and
transition/remap/handoff behavior; daemon commit full/legacy output; wakeup
diagnostics and self-hosted pull requests; runtime privacy 409/busy/auth and
atomic side effects; upload/network failures; and stable redacted 500 errors.
No parallel fixture framework or duplicate canonical operation row SHALL be
introduced.

#### Scenario: Changed behavior has exact vectors
- **WHEN** focused unit, contract, and component tables run
- **THEN** complete argv, wire payloads, decoded results, validators, call counts, no-retry behavior, and redaction match every approved delta

#### Scenario: Retained behavior remains closed
- **WHEN** approved operations and all 196 response work items are compared with runtime discovery and test references
- **THEN** every item has one verdict and all 139 unchanged items retain their public behavior

### Requirement: Complete 0.6.1 to 0.6.5 audits are reproducible offline
Maintainer evidence SHALL reproduce both official release identities, archives,
checksums, version output, recursive help, pinned source registration, dynamic
`checkin` resolution, the 209-node CLI inventory, and the 196-item response
audit. Tracked files and distributions MUST exclude `.devlocal`, release
archives, binaries, source checkouts, raw collector/audit JSON, diagnostic logs,
hash dumps, screenshots, and transient render directories.

#### Scenario: Approved contract reproduces from pinned inputs
- **WHEN** source-aware validation, deterministic double render, generated check, and source-link audit run
- **THEN** identities, counts, dispositions, mappings, generated bytes, and source links agree or a gate fails

#### Scenario: Evidence stays outside Git and packages
- **WHEN** tracked and built contents are audited
- **THEN** only approved contract, code, tests, documentation, and generated product artifacts are present

### Requirement: Delivery gates use one clean exact SHA
Strict OpenSpec validation, source-aware contract validation, deterministic
render comparison, generated freshness, source-link audit, Ruff check/format,
mypy source/tests/scripts, complete non-live pytest and live-node exclusion,
build, wheel/sdist tests, and forbidden-content audits SHALL pass at one exact
clean implementation SHA. Required CI tests and fixtures SHALL be implemented by
the Implementer; the independent Tester SHALL inspect and run them without
editing them.

The repository SHALL provide one thin versioned verification driver and the
bundled dependency-free macOS `scripts/render_terminal.swift`. The driver SHALL
verify checksum-pinned baseline/target CLI binaries, use distinct SDK checkouts,
profiles, daemons, Compose state, database, ports, and fixture names, and remove
only disposable state through failure-safe cleanup. Raw text, PNGs, logs,
credentials, private hosts, diagnostic JSON, and command evidence MUST remain
outside Git and SHALL be attached or linked only in the final Multica Tester
comment with read-back.

#### Scenario: Offline acceptance is complete
- **WHEN** implementation is presented for review
- **THEN** every mandatory offline command exits successfully at the reported candidate SHA and the worktree remains clean

#### Scenario: Independent live verification is separately evidenced
- **WHEN** human approval and the isolated target stand are available
- **THEN** Tester records tested revisions, commands, exits, assertions, MR/commit/file links, actual text, and required PNG attachments in Multica without committing evidence

#### Scenario: Cleanup preserves development evidence
- **WHEN** independent verification finishes or fails
- **THEN** disposable stand state is removed while the evidence branch, MR, commits, and repository-owned scripts remain available and unmerged/unclosed until separately authorized

### Requirement: Changed macOS output has real before and after evidence
Changed daemon status and multi-value property output SHALL be captured as actual
UTF-8 baseline and candidate text with equivalent fixtures, locale, width, and
output mode, then rendered to PNG by `scripts/render_terminal.swift`. ANSI,
TTY, and progress limitations SHALL be stated; fabricated or translated output
MUST NOT be accepted.

#### Scenario: Before and after output is comparable
- **WHEN** Tester captures baseline and candidate output for an approved visible-output case
- **THEN** the text and PNG pairs identify scenario and revision, preserve the tested output language, and show the asserted difference under equivalent conditions

### Requirement: Documentation describes one direct migration and rollback
README, API, CLI coverage, compatibility, migration, contributing,
service-usage, and release guidance SHALL describe one direct upgrade from
effective baseline `0.6.1` to maximum-tested `0.6.5`, compatibility interval
`[0.6.0,0.6.6)`, approved adaptations, retained behavior, explicit exclusions,
and one coherent rollback to SDK baseline
`a96eecf3e12a88dd7b4d56e1aafae3285fb0990c`.

#### Scenario: Consumer guidance matches implementation
- **WHEN** documentation, signatures, inventories, compatibility metadata, and fixtures are compared
- **THEN** properties, workflows, daemon identity, wakeups, runtime conflicts, errors, exclusions, and version bounds agree exactly

#### Scenario: Failed gate restores one baseline
- **WHEN** a provenance, generation, source-link, test, live, or packaging gate fails
- **THEN** all `0.6.5` implementation and claims can be reverted together without using draft or lower-target branches as a baseline
