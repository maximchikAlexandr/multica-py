## Context

The SDK models `Agent` (`src/multica_py/models/agents.py:8`) and `Squad`
(`src/multica_py/models/system.py:53`) are decoded directly by `msgspec` from
the CLI JSON output via `BaseResource._run_json_decode` / `_run_json_decode_list`
(`src/multica_py/resources/_base.py:20-49`). There is no wire/from-wire layer
for `Agent` or `Squad` today — `msgspec` populates the struct fields by name from
the JSON keys. The nested-resource pattern (`AgentResource.skills`,
`IssueResource.comments`) is already established
(`src/multica_py/resources/agents.py:15`,
`src/multica_py/resources/issue_comments.py`).

`AgentSkillResource.list` (`src/multica_py/resources/agent_skills.py:8`)
currently decodes the generic `Skill` model
(`multica_py.models.skills.Skill` with `id`, `name`, `description`,
`file_count`). The upstream `agent skill list` command actually returns skill
objects with `id`, `name`, `enabled` — the `enabled` flag is dropped by the
`Skill` decode, and `description`/`file_count` are absent. The same shape is
embedded inside the `agent get` / `agent list` responses under `skills`.

Constraints from AGENTS.md and the existing specs:

- The approved contract is the only generator input; however the
  `skills-squads-and-autopilots` family is `deferred_owner_decision` with
  `required_operation_ids: []`
  (`contracts/sdk-contract.json:3440-3450`), so `agent skill list`,
  `squads.list`, `squads.get`, and the new `squad member list` are all
  ungoverned, hand-written operations. No `contracts/sdk-contract.json` binding
  is added for `squad member list`; it mirrors the existing ungoverned squad
  operations. `approved_sdk.py` is not regenerated by this change.
- Tests are table-driven first; reuse `tests/cases/operations.py` rows and the
  existing contract test module. No new test files.
- `test_discovered_public_methods` asserts the canonical method set size; the
  new `squads.members.list` is a canonical public method, so the count rises by
  exactly one (116 → 117) and the assertion must be updated.
- `test_legacy_payload_bijection` pins SHA-256 fingerprints over
  `(resource_attr, method, args, kwargs, transport_method, expected_argv,
  stdin, timeout, stdout)` for legacy IDs 001–138
  (`tests/unit/resources/test_operations.py:98-128`). `msgspec.json.encode`
  emits ALL struct fields including defaults (verified empirically: `Agent(id="a1", name="n")`
  encodes to `{"id":"a1","name":"n","description":null,"skills":[]}` today), so
  adding `archived_at` to `Agent` and `leader_id`+`archived_at` to `Squad`
  changes the encoded bytes of the shared `_AG` / `_SQ` fixtures and therefore
  the fingerprints of every legacy row that uses them:

  - `_AG` (`Agent(id="a1", name="n")`) is the stdout for `agents.get`,
    `agents.create` (canonical + variants 01–03), `agents.update` (canonical +
    variant 01) → legacy rows 002, 004, 005, 006, 007, 008, 009 (7 rows).
  - `_SQ` (`Squad(id="s1", name="S")`) is the stdout for `squads.get` → legacy
    row 082 (1 row).
  - `legacy:001` (`agents.list`, stdout `b"[]"`) and `legacy:003`
    (`agents.skills.list`, stdout `b"[]"`) are empty-list stdouts and are
    unaffected by item-type changes.

  Total: **8 legacy fingerprints change** and must be regenerated in
  `tests/cases/legacy_payloads.py` (rows 002, 004, 005, 006, 007, 008, 009,
  082). The new `squads.members.list` row uses a fresh `manual:` id, not in
  `LEGACY_ARGV_MIGRATION`, so the 138-row bijection count is unchanged.

## Goals / Non-Goals

**Goals:**
- Decode `Agent.skills` as `tuple[AgentSkill, ...]` (typed `id`, `name`,
  `enabled`).
- Decode `Agent.archived_at` (`datetime | None`).
- Decode `Squad.leader_id` and `Squad.archived_at` (both `| None = None`).
- Add `SquadMember` and a `client.squads.members.list(squad_id)` operation with
  the exact argv `("squad", "member", "list", <squad-id>, "--output", "json")`.
- Make `AgentSkillResource.list` return the same typed `AgentSkill` (not
  generic `Skill`), so both read paths agree.
- Keep existing minimal fixtures decoding (additive optional fields).

**Non-Goals:**
- A contract binding / generator input for `squad member list`: it stays
  ungoverned, hand-written, like the existing squad and agent-skill operations.
- Regenerating `approved_sdk.py`: no contract binding is touched.
- Mutating squad members (`add`/`set-role`/`remove`): only the read operation is
  in scope for this issue.
- An enum for `SquadMember.member_type` or `SquadMember.role`: kept as `str` for
  minimal scope; a follow-up enum can be added when upstream values stabilise.
- An enum or model for `Agent.archived_at` states: a `None`/`datetime` union is
  sufficient.

## Decisions

**1. Decode `Agent` and `Squad` directly with `msgspec`, no wire layer.**
There is no `AgentWire`/`SquadWire` today and no rename is needed (all new field
names match the upstream JSON keys verbatim: `archived_at`, `leader_id`,
`skills` with `id`/`name`/`enabled`, `member_id`/`member_type`/`role`). Adding a
wire layer for a 1:1 name mapping would be unused indirection. `msgspec`
natively decodes RFC3339 strings into `datetime.datetime` for fields typed
`datetime.datetime | None`, and `null` into `None`, with no custom converter.

**2. `AgentSkill` lives in `multica_py.models.agents`, `SquadMember` lives in
`multica_py.models.system`.**
`AgentSkill` is only meaningful as the element type of `Agent.skills` and the
return of `AgentSkillResource.list`; co-locating it with `Agent` keeps the
agent model module self-contained. `SquadMember` is only meaningful as the
return of `SquadResource.members.list`; co-locating it with `Squad` mirrors the
agent choice. No cross-module import cycle: `AgentSkillResource`
(`src/multica_py/resources/agent_skills.py`) imports `AgentSkill` from
`multica_py.models.agents` instead of `multica_py.models.skills`.

**3. `Agent.skills` type change is the one breaking edit; make it additive
elsewhere.**
`tuple[str, ...]` → `tuple[AgentSkill, ...]` is a type-level break for anyone
constructing `Agent(skills=("s1",))` or indexing `agent.skills[0]` as a string.
Every other field (`archived_at`, `leader_id`) is additive with `None`
defaults. The minimal fixture `Agent(id="a1", name="n")` still constructs
because `skills` and `archived_at` keep their defaults. Note: `msgspec.json.encode`
emits ALL fields (including defaults), so the fixture bytes DO change when
`archived_at` is added — this regenerates 7 legacy Agent fingerprints (see
Decision 6).

**4. `SquadResource.members` mirrors the nested-resource pattern, including the
test wiring.**
`SquadResource.__init__` sets `self.members = SquadMemberResource(transport,
config)`, exactly as `AgentResource.__init__` sets `self.skills =
AgentSkillResource(transport, config)` (`src/multica_py/resources/agents.py:15`)
and `IssueResource` sets `self.comments = CommentResource(...)`. The new
resource is registered in `tests/cases/operations.py` via two coordinated
edits that mirror the `agents.skills`/`agent_skills` path exactly:

1. `("squads", "members"): "squads_members"` in `_NESTED_RESOURCE_ATTRS`
   (`tests/cases/operations.py:87-96`). This dict drives both
   `_resource_attr("squads.members.list")` → `"squads_members"` (line 114-120)
   and `_NESTED_DOTTED_PREFIXES["squads_members"]` → `"squads.members"` used by
   `discover_public_methods` (line 123-139). Without it, `_resource_attr`
   falls back to `parts[0]` = `"squads"`, resolving to `SquadResource.list()`
   (no args), and `test_operation` raises `TypeError: list() takes 1 positional
   argument but 2 were given`.
2. `("squads_members", SquadMemberResource)` in `RESOURCE_SPECS` (line 59-85),
   using the **flat key** `squads_members` — same convention as
   `("agent_skills", AgentSkillResource)`, `("issue_comments", ...)`,
   `("skill_files", ...)`. Do NOT use a dotted `"squads.members"` key; the
   flat key is what `_RESOURCE_MAP` (`test_operations.py:22`) looks up, and the
   dotted prefix is derived from `_NESTED_RESOURCE_ATTRS`, not from the
   `RESOURCE_SPECS` key.

This keeps the wiring symmetric with every other nested resource and makes
`test_operation` and `test_discovered_public_methods` pass with the new
canonical method `squads.members.list` (count 116 → 117).

**5. `SquadMemberResource.list` is ungoverned and hand-written.**
No `contracts/sdk-contract.json` binding is added (the family is
`deferred_owner_decision`). The method calls
`self._run_json_decode_list(("squad", "member", "list", squad_id),
SquadMember)`, which appends `("--output", "json")` in `BaseResource`. This
matches the issue's required argv exactly.

**6. Legacy fingerprint regeneration is required and mechanical.**
`msgspec.json.encode` emits ALL struct fields including defaults (verified
empirically: `Agent(id="a1", name="n")` encodes to
`{"id":"a1","name":"n","description":null,"skills":[]}` today, and will encode
to `{"id":"a1","name":"n","description":null,"skills":[],"archived_at":null}`
after the change). Adding `archived_at` to `Agent` therefore changes the bytes
of the shared `_AG` fixture, and adding `leader_id`+`archived_at` to `Squad`
changes the bytes of the shared `_SQ` fixture. The affected legacy rows are
002, 004, 005, 006, 007, 008, 009 (all use `_AG`) and 082 (uses `_SQ`) — 8 rows
total. `legacy:001` and `legacy:003` use `b"[]"` empty-list stdouts and are
unaffected. The regeneration is mechanical: after the model edits, re-run the
fingerprint computation from `test_legacy_payload_bijection`'s `payload(case)`
helper for each affected `final_id` and overwrite the corresponding entry in
`tests/cases/legacy_payloads.py::LEGACY_PAYLOAD_FINGERPRINTS` (index = legacy
number − 1). The 138-row count and bijection structure are unchanged; only 8
hash strings change. The new `squads.members.list` row is not in
`LEGACY_ARGV_MIGRATION`, so it does not perturb the bijection.

**7. Tests: rows, not files; parametrize the decoder fixtures.**
Per AGENTS.md "Table-driven first", the new decoder fixtures (Agent with skill
object + `archived_at = null`; Agent with RFC3339 `archived_at`; Squad with
`leader_id`; Squad with `archived_at = null`; Squad with RFC3339 `archived_at`;
Squad members with multiple roles) go into one `@pytest.mark.parametrize` in a
new `tests/contract/test_executor_models.py`-style? — no: reuse the existing
`tests/contract/` module pattern. Since there is no existing
`test_agent_models.py` / `test_squad_models.py`, add a single
`tests/contract/test_executor_models.py` with two parametrized tests (one for
Agent/Squad field decoding, one for SquadMember roster decoding). This is the
one new test file; it is justified because there is no existing contract test
module for agents/squads to extend (unlike `test_issue_models.py` for issues).
The argv case for `squads.members.list` is one new `_c(...)` row in
`tests/cases/operations.py`. The `agents.skills.list` row's stdout stays `b"[]"`
(empty list), so its fingerprint is stable.

## Risks / Trade-offs

- [Breaking `Agent.skills` type] → accepted; the issue explicitly requires
  typed skill objects. Callers treating skills as strings must update. The
  break is contained to one field; all other edits are additive.
- [`SquadMember.member_type` / `role` as free `str` drift if upstream adds
  values] → accepted for minimal scope; a follow-up enum can be added when
  upstream stabilises. Tracked with a `ponytail:` comment in
  `models/system.py`.
- [Legacy fingerprint drift on 8 rows] → mitigated by Decision 6: the drift is
  mechanical and expected. After the model edits, regenerate the 8 affected
  fingerprints (002, 004–009, 082) in `tests/cases/legacy_payloads.py` using the
  existing `payload(case)` helper. The bijection count (138) is unchanged.
- [`test_discovered_public_methods` count rises] → intentional: one new
  canonical public method (`squads.members.list`); the assertion is updated
  from 116 → 117 and the total case count from 140 → 141. This is the
  contracted, reviewed change to the canonical surface — not an allowlist.
- [No contract binding for `squad member list`] → intentional, matching the
  existing ungoverned squad operations; the family disposition is
  `deferred_owner_decision`.
